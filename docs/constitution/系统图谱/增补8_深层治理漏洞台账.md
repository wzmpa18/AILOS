## G1：版本号无强制 CI 校验

### 漏洞描述
增补 7 只要求 Commit Message 写图谱版本号，但没有 CI 硬拦截兜底。开发可以不写版本号直接合并代码，版本绑定规则最终变成"君子协定"。

### 利用路径（老油条视角）
```
git commit -m "fix: 优化性能"  ← 没写[图谱版本:v3.0.0]
git push origin main          ← CI 不拦截
→ 代码合并成功，版本绑定规则形同虚设
```

### 目标架构
```
git commit → pre-receive hook → 检查 Commit Message 是否含[图谱版本:vX.Y.Z]
  → 有？→ 放行
  → 无？→ ❌ 拒绝推送，返回错误信息
```

### 交付标准
| 项目 | 标准 |
|------|------|
| CI 拦截脚本 | 在 `.github/workflows/version-check.yml` 或 pre-receive hook 中实现 |
| 检查规则 | 正则 `/\[图谱版本:v\d+\.\d+\.\d+\]/`，不匹配则拒绝 |
| 告警机制 | 拦截时输出标准错误信息："提交被拒绝：Commit Message 缺少 [图谱版本:vX.Y.Z] 标注" |
| 落地阶段 | P1（账簿+治理基建） |
| 责任部门 | 技术保障中心 · 运维部署部 |

## G2：图谱无机器可读元数据

### 漏洞描述
当前所有图谱均为 Mermaid 文本（`.md` 文件），仅供人工阅读。CI 流水线无法自动比对"图谱登记的路由/服务"和"代码实际存在的路由/服务"，隐藏接口、幽灵服务永远无法被自动发现。

### 利用路径（黑客视角）
```
开发在 Controller 里加一行：
router.get('/api/hidden/bypass', async (req, res) => {
  const result = await axios.post(HUNYUAN_API_URL, ...);  ← 直连模型
  res.json(result);
});
→ 图谱没有这个路由 → CI 扫描不到 → 审计永远不知道这个旁路存在
```

### 目标架构
```
图谱 .md 文件 → 同步生成 system-atlas-v3.0.0.json → CI 扫描脚本读取 JSON
  → 比对代码中实际路由/服务/表 → 发现未登记项 → 告警/拦截
```

### 交付标准
| 项目 | 标准 |
|------|------|
| JSON 元数据文件 | `docs/constitution/system-atlas-v3.0.0.json` |
| 包含内容 | 所有路由路径、Service 文件列表、数据表列表、依赖关系、SSOT 标记 |
| 与图谱同步规则 | 图谱 .md 更新时，JSON 必须同步更新（PR 检查） |
| 落地阶段 | P1 |
| 责任部门 | 安全合规审计中心 · 审计问责部 |

### JSON Schema（示例）

```json
{
  "version": "3.0.0",
  "generated_at": "2026-08-05",
  "modules": [
    {
      "name": "vocabulary",
      "layer": "L2",
      "routes": ["/api/vocabulary", "/api/content?type=vocabulary"],
      "services": ["vocabularyService"],
      "tables": ["vocabulary_words", "vocabulary_progress"],
      "ssot_tables": ["vocabulary_words"],
      "allowed_calls": ["CoreOS Facade", "Brain AI", "vocabulary_repository"],
      "forbidden_calls": ["ReadingService", "GrammarService", "直连模型API"]
    }
  ],
  "violations": [
    {
      "id": "VC-001",
      "level": "L1",
      "file": "src/services/aiService.js:96-125",
      "type": "bypass_brain",
      "deadline": "P2"
    }
  ]
}
```

## G3：审计执行主体与周期未固化

### 漏洞描述
违宪台账有整改责任人，但"谁来定期扫代码、谁来核验台账真实性、谁来启动问责"未落到具体部门和固定周期。等于没人审，台账会慢慢变成死账。

### 利用路径（组织管理视角）
```
台账写了 VC-001 待整改 → 6 个月后 → 没人来查 → 开发继续无视 → 旁路永久保留
"反正没人审计，台账写不写都一样"
```

### 目标架构
```
安全合规审计中心（唯一审计执行主体）
  → 每月 1 次全量代码扫描
  → 出具《月度违宪审计报告》
  → 直接报治理中枢，无需提前通知开发端
  → 审计结果与模块负责人问责直接挂钩
```

### 交付标准
| 项目 | 标准 |
|------|------|
| 审计执行主体 | 安全合规审计中心 · 审计问责部（唯一主体） |
| 审计周期 | 每月 1 次（每月第一个工作日） |
| 审计产出 | 《月度违宪审计报告》 |
| 报告内容 | 违宪台账核验结果、新增违规项、超期未整改项、问责建议 |
| 问责机制 | 同类问题重复出现 3 次，自动启动问责流程 |
| 落地阶段 | P1（写入宪法，明确部门职责） |

## G4：Stage 里程碑无强制 Deadline

### 漏洞描述
违宪项绑定了对应 Stage（如"P2 内核阶段完成"），但 Stage 本身没有刚性时间节点，开发可以无限期推迟内核整改。

### 利用路径
```
台账：VC-001 整改 Deadline = "P2 内核阶段完成"
开发：P2 什么时候开始？→ 不知道，先做业务功能
→ 6 个月后 P2 还没开始 → VC-001 永远挂着
```

### 目标架构
```
Stage0（图谱）: 2026-08-05 ✅ 已完成
Stage1（账簿）: 2026-08-20（预估）
Stage2（内核）: 2026-09-15（预估）
Stage3（扫描）: 2026-09-30（预估）
...
超期自动触发一级告警 → 对应中心负责人必须复核说明原因
```

### 交付标准
| 项目 | 标准 |
|------|------|
| Stage 刚性 Deadline | P1 账簿阶段确定所有 Stage 的硬性交付日期 |
| 超期处置 | 自动触发一级告警，对应中心负责人 48 小时内复核说明 |
| 告警升级 | 连续 2 次超期 → 升级为一级违宪，启动问责 |
| 落地阶段 | P1 |

## G5：本地开发环境无直连管控

### 漏洞描述
目前所有规则都约束线上环境，本地开发环境密钥明文、可直接调用模型接口。开发完全可以在本地写直连代码，上线时再伪装走网关，代码审计根本查不到痕迹。

### 利用路径
```
本地 .env 里有 HUNYUAN_API_KEY=sk-xxx
开发在本地写：axios.post('https://api.hunyuan.com', { headers: { Authorization: process.env.HUNYUAN_API_KEY } })
测试通过 → 部署到生产时把直连代码包在 if(process.env.NODE_ENV==='production') 里
→ 审计只看生产代码，完全发现不了
```

### 目标架构
```
本地开发环境：
  - 无真实模型密钥（仅 Mock 接口）
  - 本地直连模型请求自动拦截告警
  - 生产密钥仅运维端持有（CI 注入，开发端无权限接触）
```

### 交付标准
| 项目 | 标准 |
|------|------|
| 密钥隔离 | 本地 `.env` 不含真实 API Key，仅含 Mock 端点 |
| 直连拦截 | pre-commit hook 扫描代码中是否含直连模型 API 的 URL |
| 生产密钥管控 | 生产密钥仅通过 CI/CD 注入，开发端不可见 |
| 落地阶段 | P2（内核落地时同步实施） |
